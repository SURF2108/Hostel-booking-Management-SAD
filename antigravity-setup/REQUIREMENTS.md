# Requirements discovery and scope
## Mandatory source audit
Recursively inventory diagrams/ and README.md; identify file types, names, and git revision. Open each diagram visually at readable resolution; parse PlantUML/Mermaid/draw.io/XML sources when available. For PDF diagrams render pages; for raster diagrams zoom and inspect labels, connectors, cardinalities and arrow directions. Do not infer unreadable text. Record per-file findings and ambiguities in docs/SOURCE_AUDIT.md. If a file cannot be opened, try available local renderers or source export; record what remains unverified. Never claim full fidelity if material diagrams are unreadable.
Extract actors and use cases, class fields/operations/relationships, sequence message order, activity branches, state transitions, component boundaries, deployment constraints and any other diagram types actually present. Do not assume every type exists. Resolve conflicts using explicit source evidence and document decisions. Keep terminology consistent with diagrams. Distinguish confirmed, inferred and optional requirements. Use the smallest coherent interpretation when ambiguous; continue independent work rather than interrupting for minor decisions.
Create docs/REQUIREMENTS.md with numbered functional/nonfunctional requirements and docs/TRACEABILITY.md mapping source file + element -> requirement -> role -> screen -> endpoint -> service/model -> test. Include a state transition table and authorization matrix. Cover all confirmed flows and preserve scope; no silently omitted actor or feature.
## Provisional defaults only (not verified repo facts)
Likely workflows: authentication; hostel/room/bed discovery and availability; booking request or reservation; user booking history; cancellation; staff/admin inventory and booking management. Add approval, allocation, payment, check-in/out, reports, notifications or other roles only if supported by diagrams or necessary for a coherent confirmed workflow. Do not impose hotel-style nightly booking on semester-based allocation or vice versa. Do not assume gender restrictions, fee rules or approval steps. Use exact actors and states from sources. If payments are required, use clearly labeled local simulation unless a real integration is explicitly authorized; never collect card details. Use INR only if context supports it; otherwise document demo currency choice. Public registration must never grant staff privileges. Seed fictional data only.
